# Ask Matilde: Langdock integration

Updated 2026-11-15. Ask Matilde (formerly Writing assist) was implemented at the owner's request. Backlog: AI-01 through AI-04 in ROADMAP.md.

## Available experience

In Settings → Connections, save a Langdock API key in Keychain, select the API address and region, load available models and choose a compatible chat model. No model is selected automatically. Ask Matilde (formerly Writing assist) lives in one window-toolbar control: clicking it starts a manual review or cancels a running one; its menu holds Ask Matilde… (⇧⌘A), Review now, pause/resume and saved history.

Manual review uses the active writing goal and returns zero to three comments about clarity, structure or support, with optional replacements. Floating cards overlay the writing surface 16 points beyond the actual text column, beside their TextKit passages, and follow scrolling. They reserve no sidebar width or editor layout space. The stash opens above them. Compact previews expand on selection; selected passages receive a temporary highlight and nearby cards stack without overlap. Smaller windows use compact comment buttons with popovers. The side pane shows only comment cards and threads; review controls are in the toolbar. Clicking a quote selects its source. Replacements require acceptance and remain undoable through the native editor. Earlier runs remain accessible in local history.

Reviews are stored in the workspace SQLite database, scoped to draft identity. New branches start independent histories. A hash includes title, goal and body. Any change cancels an in-flight request. Comments stay on their passages (see “Comment anchoring” below); title or goal changes no longer hide them. Saved source/revision data allows anchors to be checked again on reopen; late responses cannot apply to another draft. Multiple disjoint external edits are conservatively treated as one changed span. Exact quotes plus prefix/suffix must identify an unambiguous, nonoverlapping UTF-16 range. Acceptance rechecks the revision and source.

## API and context

The native URLSession client uses Bearer authentication with `POST /openai/{region}/v1/chat/completions` and `GET /openai/{region}/v1/models`. Default address is `https://api.langdock.com`; EU and US are selectable. Dedicated installations can include `/api/public` in their base URL. HTTPS is required and redirects are rejected to avoid forwarding credentials. [Langdock OpenAI-compatible endpoint](https://docs.langdock.com/en/developer/completion-api/openai).

The request uses JSON mode (`response_format: {"type":"json_object"}`), not strict API-enforced JSON Schema. Local decoding checks completion status, bounded fields, comment count and anchors before presenting results. JSON-mode review replies have been verified with the configured model; compatibility across other models remains unverified. Requests have timeouts, cancellation, a bounded response size and one bounded retry on rate limiting. Upstream response bodies and keys are excluded from errors.

Reviews supply the active draft title, goal and body, followed by the draft's existing comments (AI-19). Replies also supply the relevant comment, the new question and the thread's earlier messages (see “Whole-draft context and prompt caching” below), with the same image/path redaction. Stash, other drafts and image files are excluded; Markdown image references and recognized absolute local paths are scrubbed. This is a defined context boundary, not a general-purpose secret detector. The writing is treated as untrusted review material. Credentials remain in Keychain and, after successful access, in a process-only cache shared by requests; save/remove refreshes that cache. No credential is written to settings or disk outside Keychain. Ad-hoc rebuilt binaries can still require authorization on first access because their designated requirements change; stable Developer ID signing is a separate follow-up. Reviews remain locally persisted. The Connections screen explains what is sent.

## Automatic reviews and replies

After meaningful body or goal changes and thirty seconds without further draft edits, Ask Matilde reviews the active draft if the app is active, no board/transition/dialog is open, and a model plus session-authorized key are available. Saving the key or making a manual request authorizes the current process session; automatic reviews never read Keychain interactively. Opening a draft alone does not send it. Formatting-only changes are ignored; identical attempted revisions are not retried automatically. Pause/resume is available from the Ask Matilde toolbar menu and persists across launches. Draft edits/switches and pause cancel pending work. Existing open threads carry into the next review, and suggestions that repeat an existing comment are dropped (see “Existing comments in reviews” below).

Expanded comments have a reply field. Successful replies are saved with the comment and may update its optional rewrite. They never modify the draft until Accept rewrite is chosen. Messages appear and persist immediately with pending delivery state; the thread shows Thinking and Cancel while waiting. Failed or cancelled requests keep the question and offer Retry without duplicating it. Interrupted pending requests recover as failed on reopen; stale responses are discarded. New messages scroll into view. User and assistant messages have subtly different surfaces. The reply composer stays fixed below the scrolling transcript, and expanded cards shorten when focus leaves the conversation, preserving the thread. There is no Dismiss control. Cards animate their height with Reduce Motion support, show hover/focused styling, and autofocus the input every time they open. Source snapshots and threads are local SQLite metadata; new branches have independent histories.

## Asking about selected text

Select body text and click the small Ask Matilde action, use the right-click menu, or press Shift-Command-A. Without a selection the shortcut and menu items use the paragraph around the insertion point, trimmed of surrounding whitespace; on an empty line they start a review. The anchored thread opens immediately with its composer focused; no API request happens until Send. Exact selection ranges support repeated phrases and Unicode. Selecting an existing open thread’s exact range reopens it. These threads share review history, acceptance and cancellation behavior; automatic reviews preserve them.

### Streaming chat replies (2026-09-15)
Chat replies request `stream: true` on the existing OpenAI-compatible endpoint, retaining JSON mode. SSE deltas are bounded, cancellation-aware, and coalesced to approximately 25 UI updates per second. The prompt requests the answer field first; a safe partial-string decoder displays text while holding incomplete escapes/surrogate pairs. If a model orders fields differently, the answer appears on completion. Reviews remain non-streaming.

Partial answer text is transient. Only a complete stop/DONE response passing the existing JSON/size/refusal checks is persisted or supplies a new accepted rewrite. Interrupted requests retain the failed user question and Retry behavior. No raw JSON or incomplete replacement is shown. The transcript uses plain messages with differently colored role labels and a sticky composer.

Verified with synthetic streaming transport (including incremental updates, JSON mode), escape/Unicode, refusal, truncation and size-limit tests. Live provider streaming has not yet been exercised; no owner writing was submitted during these checks.
Reference: https://docs.langdock.com/en/developer/completion-api/openai

### Editable guidance (2026-11-15)
Settings → Ask Matilde shows the guidance that shapes reviews and replies, prefilled with the built-in default, with Reset to Default. It is stored in UserDefaults under `writingAssist.guidance`; blank text falls back to the default and input is capped at 4,000 characters. Each system prompt is the guidance followed by a fixed part the user cannot edit: the review or reply task, the instruction to treat the draft as untrusted writing, and the JSON response shape the app parses (`WritingAssistPrompt.swift`). The fixed part states that it takes precedence over the guidance. Local response validation is unchanged, so guidance that asks for another format still fails safely. Unit tests cover custom guidance in review, reply and streamed reply requests and the fixed part in every prompt; live provider behavior with custom guidance has not been checked.

### Comment anchoring and toolbar (2026-11-15)
AI comments and private comments follow the same rule (`CommentAnchor` in `UserComments.swift`, applied to reviews in `ReviewTracking.swift`). Each change is diffed into one UTF-16 replacement. Edits before a passage shift it; edits inside it grow or shrink it; deleting part of it shrinks it to what remains; replacing exactly the passage keeps the comment on the new text. A comment leaves the margin only when its whole passage is deleted (AI comments get status `removed`, private comments detach) or when it is deleted explicitly (trash in the thread footer or the comment popover). The quote and up to 40 characters of context are kept, so undo restores a removed comment. After every change the range, quote, context, source and revision are saved, so reopening a draft or external edits re-anchor from the saved source and then by quote/context. Title and goal changes keep every comment. A suggested rewrite can be accepted only while its passage still equals the text it was written for; replies that offer a new rewrite target the current passage. Automatic-review errors show as the toolbar icon and tooltip; manual review, accept and save errors use the app alert.

### Whole-draft context and prompt caching (AI-17, 2026-11-18)
Chats about a passage (selected text, the current paragraph, or a review comment) always send the whole current draft, and mark the passage as `focus` with the text just before and after it. Requests are built by `ReplyPrompt` (`ReplyPrompt.swift`) in a fixed order so Langdock's automatic prefix caching can reuse everything but the newest turn:

1. system: guidance followed by the fixed task and JSON format (`WritingAssistPrompt.reply`), the same for every thread;
2. user: `{"draft":{body,goal,title}}`, the whole draft as it was when the thread started, the same for every thread started on that version of the draft;
3. user: `{"comment":…}`, the comment the thread is about (`started_by` writer or review, explanation, the review's own rewrite);
4. the earlier turns, replayed exactly as they were sent: user turns from `ReviewMessage.prompt`, assistant turns as `{"answer":…,"replacement":…}`;
5. user: `{"draft_update":…,"focus":{after,before,passage},"question":…}`.

All JSON uses sorted keys and no escaped slashes, the request body is an Encodable struct, and nothing time- or ID-based is sent. Messages 2–3 are frozen in `ReviewComment.replyContext` together with the draft as last described; they and each user turn are saved in the `writing_reviews` JSON in SQLite, so the prefix stays identical across relaunches. Failed turns are not replayed and don't advance the context.

Document changes: the draft goes in once at thread start; edits since the previous turn are appended to the newest turn as `draft_update` (title/goal as new values, the body as one removed/inserted span with 80 characters of context, or the full new body when the span exceeds 16 KB). Trade-off: re-sending the current draft every turn would be simpler but every edit would invalidate the cached draft and the whole history behind it; appending updates keeps the prefix cached at the cost of the model applying edits itself. For long threads with many edits the update chain grows; once replayed history and the new turn exceed 120 KB, the context is rebuilt once from the current draft with the last 12 messages folded into the comment block as plain text, then the thread is append-only again. Earlier messages beyond those 12 are then no longer sent. The draft limits are unchanged (100 KB body, 10 KB title and goal; larger drafts are refused with the existing message).

Langdock's OpenAI-compatible endpoint routes to OpenAI/Azure deployments, caches long shared prefixes automatically (OpenAI's minimum is 1,024 tokens, so short drafts may not be cached at all) and removes cache controls from requests, so no explicit breakpoints are sent; cached tokens appear in `usage.prompt_tokens_details.cached_tokens`. If an Anthropic endpoint is added later, breakpoints belong after message 1 and after the last replayed turn. Automatic and manual reviews still send one draft message (now with sorted keys); their draft changes with every edit, so only the system prompt is shared. Unit tests: `ReplyPromptTests`. Live cache hits have not been measured.

### Existing comments in reviews (AI-19, 2026-11-23)
User report: Ask Matilde “does not read existing comments and keeps pointing out things that are already commented”. Root cause: review requests sent only the title, goal and body. Neither the Ask Matilde comments (open, accepted or dismissed, with their replies) nor the writer's private comments reached the model, so it had no way to know what was already said. The only guard was after the response: a new suggestion was dropped when its quote was character-for-character identical to an earlier review comment's quote. A slightly longer or shorter quote on the same sentence, any point already made in a private comment (or one an AI tool left through the MCP server), and anything archived slipped through.

Now (`ReviewContext.swift` in MatildeKit, used by both apps through `WritingReviewModel`):

1. system: guidance + fixed task and format (unchanged, cacheable);
2. user: `{body,goal,title}`, the whole draft (unchanged, cacheable);
3. user, only when the draft has comments: `{"existing_comments":[…]}`, each with `by` (`matilde`, `writer`, `ai_tool`), `kind` (`suggestion`, `question`, `note`), `status` (`open`, `resolved` = rewrite accepted, `dismissed` = archived), `passage` as it reads now, `passage_when_commented` when it has since been reworded, `comment`, `suggested_rewrite` and the last four `replies`.

The comment list is the only part that changes between reviews of one draft, so it goes last and the stable prefix stays byte-identical. It covers every Ask Matilde comment the writer can see or has decided on (newest copy of carried threads; open comments of superseded reviews and deleted passages are left out) and private comments, archived ones as dismissed. Texts are scrubbed like the draft, shortened (600 characters per passage/comment, 400 per reply) and capped at 60 comments / 40 KB, open ones first. The fixed review format tells the model not to raise a point any of them covers, whatever its status, unless the passage changed meaningfully since.

After the response, `ReviewDeduplication` drops a new suggestion that sits on essentially the same passage as an existing comment (≥ 60% of the longer range shared) or overlaps it and makes a similar point (at least two key words in common covering 40% of the shorter comment's). Comments whose passage has been reworded (under 70% word overlap with `ReviewComment.reviewedQuote`, the passage as first commented; nil in older reviews, which count as unchanged) don't block anything. The old exact-quote check stays.

Not changed: thread chats still send the whole draft plus only their own thread; the MCP server's `read_note` already returns the private comments, and `add_comment` now returns the existing comment instead of adding the same comment on the same passage twice. `reviewedQuote` is local to the device's `writing_reviews` JSON and isn't part of the synced thread record yet.
